# Step 778 — element admins in the sign-in (node step 778)

**Asked by:** the core's main agent. The owner's words, 2026-11-17: «elementAdmin001…elementAdmin980 … во всех проектах могут быть одинаковыми изначально создать и жёстко пришить использовать только эти названия»; «При рождении элемента просим ввести e-mail и пароль».

## What was built

- `lib/element-admin-role.ts` — the fixed family `elementAdmin001…elementAdmin980` (`/^elementAdmin(\d{3})$/`, 1 ≤ n ≤ 980); not in
  `ALL_ROLES`.
- `lib/auth/node-users.ts` — `grantElementAdmin`, `createUser`, `setPassword`, `stripRole`; the batch (`addRole`, `removeRole`,
  `update`) accepts the family, an architect only.
- `app/api/node-users/[[...path]]/route.ts` — `POST /element-admin`, `POST /` (create), `PUT /<id>/password`, `POST /strip-role`;
  a refusal by role names `requires: ["architect"]`.
- `app/api/admin/users/[id]/route.ts` — PATCH: granting or removing an element-admin role needs the node architect (403 otherwise).
- `app/api/users/[id]/route.ts` — the proxy accepts the family.
- `/api/session` and the users list already returned roles from the database as stored — no change needed; the test proves both.
- Password rule for these doors: 8–200 characters (the service had no rule of its own besides «required»).
- README section «Element admins (step 778)»; `npm run test:element-admins`.

## Checks (evidence)

`npm run test:element-admins` — a production build into `.next-t778` (removed after), its standalone server on a free loopback port,
a fresh database in a temporary folder: **14 checks passed** — no key / wrong key → 401; a role outside the family (000, 981, `admin`,
wrong case, two digits) → 400; a non-architect actor → 403 with `requires: ["architect"]` on all four doors; an existing e-mail in
another case → `created:false`, the old password still signs in through the real NextAuth form and the request's password does not;
no account without a password → 400 `password-required`; `/api/session` by the real cookie returns `elementAdmin007`; the list's role
filter finds both holders; PUT password works and own password → 403; the batch and the admin PATCH refuse a non-architect; strip-role
→ `count: 2`, then 0, another role stays; the journal holds `element-admin` / `users-tab` rows by the actor and no password text,
nor does the server log.

Spoiled on purpose: the PATCH counterweight turned (`!callerIsArchitect` → `callerIsArchitect`) — the test failed with «actual 200,
expected 403»; restored, green again.
