# Step 796-1 — the architect of a fresh server is claimed by e-mail (node step 796-1)

**Asked by:** the core's main agent; approved by the owner (Telegram 690). Short way (2a).

## What was built

- `lib/auth/claim.ts` — `issueEmailClaim(email)` keeps only the SHA-256 of the trimmed lower-cased e-mail with `kind: "email"`;
  `claimKind()`, `claimMatchesEmail()`, `firstAccountGate()` (the register form's gate for the first node account), `claimStatus()`
  (the GET answer), `architectTokenOk()` (the door's lock, moved out of the route). A claim file of 739 without a kind reads as a code
  claim. A new claim of either kind replaces the old one.
- `app/api/claim/route.ts` — `POST {email}` → `{ ok, kind: "email" }`; a body-less POST (or a body without `email`) → the code of 739,
  so older servers do not break; bad JSON / bad e-mail → 400; the lock and loopback as before; 409 once a node account exists.
  `GET` → `{ ok, pending, kind: "email" | "code" | null, claimed }`.
- `lib/auth/register.ts` — the first node account goes through `firstAccountGate`: under an e-mail claim only the claimed e-mail (any
  letter case) passes, becomes the architect and ends the claim; another e-mail → `claim-email`. The second account is a user as before.
- `lib/auth/sqlite-adapter.ts` — unchanged: Google and the magic link still refuse the first account while any claim waits (D29).
- The register form — an e-mail claim shows no code field, only the line `claimEmailOnly` above the form (an `Alert`); the same line
  is the refusal text. Strings in English and Russian; other languages fall back to English, as `claimRefused` does.
